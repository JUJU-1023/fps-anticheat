# L2 서버 검증 규칙

**계층**: L2 (Server Authoritative Validation)
**적용 버전**: W7 종료 시점 (2026-09)
**스키마**: `anticheat` v1.1

---

## 이 문서의 목적

검증기 4종의 규칙, 임계값, 그리고 **그 임계값을 왜 그 숫자로 정했는지**를 남긴다.
발표자료의 L2 표는 이 문서를 출처로 한다.

임계값에 근거가 없으면 "왜 110ms 인가"라는 질문에 답할 수 없다.
실측 없이 정한 값은 이 문서에 **잠정**으로 표시한다.

---

## 공통 설계 원칙

### 1. 서버가 아는 값만 판정에 쓴다

클라이언트가 보낸 위치·RTT·틱은 조작 가능하다.
판정에 쓰는 값은 서버가 직접 측정하거나 계산한 것뿐이다.

| 쓰는 값 | 출처 |
|---|---|
| RTT | `NetworkTransport.GetCurrentRtt()` |
| 위치 | 서버가 입력으로 시뮬레이션한 결과 |
| 시각 | `Time.realtimeSinceStartup` |
| 반동 | `WeaponConfig` 결정론적 패턴 |

클라이언트가 보낸 `input.tick` 은 **게임플레이 게이트에만** 쓰고 위반 판정에는 쓰지 않는다.

### 2. 클라이언트 틱과 서버 틱은 다른 시간축이다

두 카운터는 서로 다른 시점에 0에서 시작한다.
실측에서 `server_tick=6171` 일 때 `client_tick=1930` 으로 4,241틱 차이가 났다.
직접 비교하는 검사는 성립하지 않는다. 같은 축 안에서 `lastProcessedTick` 대비 변화를 본다.

### 3. 판정할 수 없으면 무죄

되감기 이력이 요청 시각까지 닿지 않으면 그 프레임의 판정을 **보류**한다.
안티치트에서는 놓치는 것보다 억울하게 잡는 쪽이 훨씬 나쁘다.

같은 이유로 측정 불확실성은 피고에게 유리하게 더한다.
V-TIME-01 의 20Hz 양자화 보정이 그 예다.

### 4. 임계값은 실측 분포를 보고 정한다

W6 에서 `input_count` 실측 분포(1,482 샘플, 94%가 정확히 6, 지터 ±2)를 보고
토큰 버킷 용량을 20으로 정했다. 창 단위 카운팅이었다면 44건이 오탐이었다.

추정으로 정한 값은 아래 표에 **잠정** 으로 표시하고 W7 Day 5 측정 후 갱신한다.

### 5. 서버 권위 구조는 원래의 공격 경로를 막는다

계획 단계의 검사가 실제로는 발화하지 않는 경우가 반복해서 나왔다.
그때는 검사를 버리는 게 아니라 **남은 관측 가능한 신호를 다시 찾는다.**

| 원안 | 발화하지 않는 이유 | 대체 신호 |
|---|---|---|
| 위치 델타 속도 검사 | 서버가 입력으로 직접 시뮬레이션 | 입력 수신율 (토큰 버킷) |
| 벽 너머 피격 | 되감은 월드에서 벽이 먼저 명중 | 차폐된 적의 조준선 추적 시간 |

## 전제 조건: 레이어 구성

**이 구성이 깨지면 검증기 전체가 무의미해진다.** W7 Day 1 에서 실제로 겪었다.

| 레이어 | 대상 | 히트스캔 마스크 | 차폐 마스크 |
|---|---|---|---|
| `Default` | 맵 지형·벽 | 포함 | 포함 |
| `Hitbox` | 되감기 히트박스 (런타임 생성) | 포함 | 제외 |
| `Player` | 플레이어 루트 (CharacterController) | **제외** | 제외 |

`Player` 를 마스크에 넣으면 현재 위치의 캡슐이 되감긴 히트박스보다 먼저 명중해
**랙 보상이 계산은 되지만 판정에 반영되지 않는다.**

측정으로 확인한 증상:

| | 명중 | 헤드샷 | 비율 |
|---|---|---|---|
| match 14 (수정 전) | 196 | 6 | 3.1% |
| match 16 (수정 후) | 30 | 5 | **16.7%** |

DLL 빌드 시각(05:59)이 두 세션 사이에 위치해 빌드 효과로 확정했다.

`Hitbox` 는 Layer Collision Matrix 에서 전면 해제한다.
레이캐스트는 매트릭스가 아니라 `layerMask` 인자를 쓰므로 영향받지 않는다.

## V-MOVE-01 · 이동 입력 검증

| 항목 | 값 |
|---|---|
| 구현 | `AntiCheat/L2/MovementValidator.cs` |
| 조치 | 입력 폐기 (`Simulate()` 미호출). 롤백이 아니라 "서버가 움직여주지 않는다" |
| severity | 2 |

### 사유 코드

| reason | 탐지 대상 |
|---|---|
| `RateExceeded` | 토큰 버킷 고갈 = 스피드핵 |
| `TickReplay` | 이미 처리한 틱 재전송 |
| `TickAhead` | 직전 처리 틱 대비 과도한 점프 |
| `BadInput` | NaN / 무한대 / move 크기 초과 |

### 임계값

| 항목 | 값 | 근거 |
|---|---|---|
| 충전 속도 | 60/s | 정상 FixedUpdate 주기 |
| 버킷 용량 | 20 | 실측 `input_count` 최대 12에 여유 |
| 최대 틱 점프 | 120 | 패킷 손실 2초분 |
| 스폰 유예 | 3s | 접속 직후 입력이 몰려 도착 (실측: 11개/틱) |

### 검사 순서가 중요하다

값 위조 → 수신율 → 틱 이상 순이다.
틱 검사를 먼저 하면 스피드핵이 `TickReplay` 로 분류되어 실제 원인이 가려진다.

순서 교정 전후 비교:

| | TickReplay | RateExceeded |
|---|---|---|
| match 8 (교정 전) | 7,154 | 7,376 |
| match 9 (교정 후) | 1,627 | 10,772 |

## V-FIRE-01 · 발사 속도 검증

| 항목 | 값 |
|---|---|
| 구현 | `AntiCheat/L2/FireRateValidator.cs` |
| 조치 | 발사 거부 |
| severity | 2 |
| reason | `RateExceeded` |

### 왜 틱 간격이 아니라 서버 실시간인가

기존 검사는 `input.tick` 간격을 봤다. 그런데 `input.tick` 은 클라이언트가 정하고,
V-MOVE-01 은 입력 **개수** 만 60/s 로 제한할 뿐 틱 **증가폭** 은 120까지 허용한다.

```
초당 60개 전송, 매번 틱을 8씩 증가
  틱 점프 8  <  MaxTickJump 120       → V-MOVE 통과
  발사 간격 8 >= FireIntervalTicks 6  → 매 입력마다 발사
  결과: 초당 10발이 초당 60발
```

이동 속도는 변하지 않으므로 V-MOVE 로는 관측되지 않는다.

### 왜 단순 간격 검사가 아니라 토큰 버킷인가

`now - lastFire < interval` 은 지터에 취약하다.
회선이 끊겼다 복구되면 입력 20개가 한꺼번에 도착하는데, 이는 게임시간 333ms 분량이라
원래 3발이 나가야 정상이다. 간격 검사는 1발만 내보내고 나머지를 위반으로 찍는다.

### 역할 분담

| 검사 | 기준 | 목적 |
|---|---|---|
| 틱 간격 (`WeaponSystem`) | 게임시간 | 게임플레이 게이트. 지터에서 공정 |
| 토큰 버킷 (`FireRateValidator`) | 서버 실시간 | 위반 판정 |

### 임계값

| 항목 | 값 | 근거 |
|---|---|---|
| 충전 속도 | 10/s | 무기 연사속도 |
| 버킷 용량 | 4 | 400ms 버스트 흡수. **잠정** |
| 유예 | 2s | 접속·리스폰 직후. 유예 중에도 차단하되 기록만 안 한다 |

## V-LOS-01 · 시야 검증

| 항목 | 값 |
|---|---|
| 구현 | `AntiCheat/L2/VisibilitySystem.cs`, `Combat/WeaponSystem.cs` |
| severity | 3 |

### 사유 코드

| reason | 내용 | 기대 |
|---|---|---|
| `BlockedHit` | 히트 성립 후 벽 차폐 재확인 | **0건** |
| `OccludedTracking` | 차폐된 적을 좁은 각도로 지속 추적 | 월핵 탐지 |

### `BlockedHit` 은 왜 0건이 기대값인가

`FireHitscan` 은 되감은 월드에서 레이캐스트를 쏘고, 벽이 더 가까우면
`GetComponentInParent<PlayerRewind>()` 가 null 이라 히트가 성립하지 않는다.
벽 너머 피격은 구조적으로 불가능하다.

그럼에도 남겨두는 이유는 **레이어 마스크가 잘못 설정되면 조용히 뚫리기 때문**이다.
회귀 방어선이고, 0건이라는 사실 자체가 근거가 된다.

### `OccludedTracking` 의 판정

```
20Hz, 각 (관찰자 A, 대상 B) 쌍에 대해
  관찰자 눈  : A 의 현재 위치 + EyeOffset
  대상 중심  : now - (RTT_A/2 + 보간지연) 시점의 되감은 몸통 중심
  차폐 판정  : 눈 -> 중심, World 레이어만
  추적 판정  : 차폐 && 조준각 < TrackConeDeg  -> 누적 += dt
               아니면 누적 -= dt * 2 (감쇠)
```

관찰자를 되감지 않는 이유는 클라이언트 예측 때문이다. A 는 자기 위치를 현재로 본다.
대상만 되감아야 A 화면에 그려진 상태와 일치한다.

감쇠를 쓰는 이유는 하드 리셋이면 월핵이 주기적으로 시선을 떼서 회피할 수 있어서다.

### 임계값

| 항목 | 값 | 상태 |
|---|---|---|
| `TrackConeDeg` | 5° | **잠정** |
| `TrackViolationSec` | 2.0s | **잠정** |
| `TrackClearSec` | 0.5s (히스테리시스) | |
| `TrackCapSec` | 5.0s | |
| `FovHalfDeg` | 55° | 카메라 FOV 와 맞출 것 |
| `OccludeMargin` | 0.05m | |

에피소드당 1회만 보고한다. 누적이 상한에 붙어 있는 동안 매 프레임 보고하면
초당 20건이 쌓여 `occurrences` 가 의미를 잃는다.
현재 구조에서 `occurrences` = **추적 에피소드 횟수** 다.

### 알려진 오탐 요인 (미해결)

몸통 중심 한 점으로만 차폐를 판정한다.
상자 뒤에 웅크린 적처럼 **일부만 보이는 상황**에서 중심은 가려져 있고
플레이어는 보이는 부분을 겨눈다. 이것이 추적으로 집계된다.

Day 5 정상 30분 측정에서 오탐의 주요 원인이 될 가능성이 있다.
대응 후보:

1. 머리·몸통 두 점을 보고 **둘 다** 가려질 때만 차폐로 센다 (가장 정확)
2. `TrackConeDeg` 를 좁힌다
3. `TrackViolationSec` 을 올린다

실측 전에는 고치지 않는다.

## V-TIME-01 · 반응시간 검증

| 항목 | 값 |
|---|---|
| 구현 | `AntiCheat/L2/ReactionTimeValidator.cs` |
| 조치 | **기록만.** 차단하지 않는다 |
| severity | 단발 1 / 반복 3 |

### 사유 코드

| reason | 조건 |
|---|---|
| `FastReaction` | 인간 하한 미만 1회 |
| `FastReactionRepeated` | 최근 20회 중 5회 이상 |

### 정규화

`VisibilitySystem` 이 되감은 기하로 판정하므로 `spotTime` 은
"서버가 안 순간"이 아니라 **"A 화면에 그려진 순간"** 이다.
다운링크(RTT/2)와 보간 지연은 이미 반영돼 있어 업링크만 뺀다.

```
raw      = fireArrival - spotTime = reaction + RTT/2
adjusted = raw - RTT/2
```

현재 서버 위치로 판정했다면 `raw - RTT - 보간지연` 이어야 한다. 값은 같다.
**두 방식을 섞으면 틀린다.**

### 20Hz 양자화 보정

가시성 루프가 20Hz 라 실제 시야 확보보다 최대 50ms 늦게 SPOT 을 잡는다.
`spotTime` 이 늦어지면 반응시간은 그만큼 짧게 측정된다.
즉 측정값은 실제보다 평균 25ms, 최대 50ms 빠르다.

임계 110ms 에서 이 편향은 무시할 수 없으므로 위반 조건에 불확실성을 더한다.

```
adjusted + 50ms < 110ms      →  실효 임계 60ms
```

측정으로 확인한 효과: 92ms 건이 나왔으나 보정 덕에 오탐으로 찍히지 않았다.
코너 프리에임으로 설명되는 값이고, 보정이 없었다면 위반이었다.

### 왜 차단하지 않는가

확률적 지표다. 코너를 미리 겨누고 있다가 적이 나타나면 사람도 0ms 에 가까운
반응이 나온다. 정당한 플레이다. 기록만 하고 W13 Trust Score 의 입력으로 쓴다.

### SPOT 당 1회만 측정

연사를 시작하면 초당 10발이 나간다. 매 발마다 같은 SPOT 을 기준으로 재면
두 번째부터 점점 커지는 무의미한 값이 분포에 쌓인다.

### 임계값

| 항목 | 값 | 상태 |
|---|---|---|
| `ThresholdMs` | 110 | **잠정** |
| `SpotQuantizationMs` | 50 | 루프 주기에서 유도 |
| `WindowSize` | 20 | |
| `RepeatLimit` | 5 | |

## 분석 시 주의

### `spot_event_id` 는 서버 프로세스 스코프다

`VisibilitySystem._nextSpotId` 는 1부터 시작하고 서버 재시작 시 재발급된다.
반드시 `(match_id, spot_event_id)` 복합키로 조인할 것.

단독 조인 시 실제로 겪은 증상: 이전 세션의 SPOT 과 이번 세션의 FIRE 가 붙어
반응시간이 −24분으로 나왔다. W12 190세션에서는 id 가 수백 번 재사용된다.

### `is_headshot` 과 `event_type`

`HeadDamage` 가 체력 이상이면 헤드샷은 항상 즉사하고 `event_type` 이 `KILL` 이 된다.
**헤드샷은 `HIT` 로 남을 수 없다.** 헤드샷 비율은 `HIT + KILL` 을 분모로 계산할 것.

### 시각은 UTC 로 저장된다

VM 이 UTC 로 동작한다. `server_time`, JSONL `ts`, Prometheus, Loki 모두 UTC 기준이다.
표시할 때만 변환한다. VM 시계를 KST 로 바꾸면 세션 경계가 어긋난다.

### 텔레메트리 초기화

`TRUNCATE` 와 `.ingest_offset.json` 삭제는 **반드시 함께** 한다.
하나만 하면 ingester 가 "이미 읽었다"고 판단해 JSONL 원본이 있어도 영구히 건너뛴다.
`infra/scripts/reset_telemetry.sh` 를 쓸 것.

### 알려진 결함

F10 을 껐다 켜면 `_rapidTick` 이 리셋되어 서버의 `lastProcessedTick` 보다
뒤에서 시작하고 `TickReplay` 가 대량 발생한다.
**검증기 오탐이 아니라 하네스 문제다.** 측정 시 F10 은 한 번 켜서 유지할 것.
W11 컨트롤 패널로 옮길 때 정리한다.

### 트리거봇 측정 조건

봇은 조준선에 적이 들어와야 발사한다.
미리 겨누지 않으면 SPOT 과 발사 사이에 사람이 조준하는 시간이 끼어
그것이 반응시간으로 측정된다.

```
1. F10 끈다
2. B 가 벽 뒤로 완전히 숨는다
3. A 가 B 가 나올 지점에 조준선을 고정하고 대기
4. B 가 걸어나온다 -> 자동 발사
```

`ForgetSec` 가 0.5초이므로 재시도할 때 그보다 오래 가려져야 SPOT 이 새로 발생한다.
