## 2. 측정 환경

### 2.1 맵

| 항목 | 값 |
|---|---|
| 맵 버전 | `w7-map-1.0` |
| geomHash | `B2EB9154` |
| 크기 | 75 × 30 m, 바닥 상면 y=0 |
| Zone A (개활지) | X −45 ~ 0. 볼록한 빈 직사각형 |
| Zone B (엄폐) | X 0 ~ 30 |

맵은 `MeasurementMapBuilder` 가 코드로 생성한다. 씬 파일을 손으로 편집하지 않으므로 재현 가능하고, 레이어 지정 실수가 원천 차단된다.

모든 지오메트리는 `CreatePrimitive(Cube)` 로만 만든다. 보이는 메시와 콜라이더가 정의상 일치하므로, 장식 모델에서 생기는 "사람은 보이는 대로 엄폐하고 시스템은 콜라이더로 판정"하는 불일치가 없다.

#### Zone A 의 볼록성

S1 구역은 볼록한 빈 직사각형이다. 볼록 영역 내부의 두 점을 잇는 선분은 영역을 벗어나지 않으므로 **차폐가 기하학적으로 불가능**하다.

따라서 S1 에서 V-LOS 가 발화하면 임계값 문제가 아니라 버그로 확정할 수 있다. "우연히 장애물이 없어서 안 걸린다"가 아니라 "구조적으로 걸릴 수 없다"이다.

### 2.2 히트박스 (실측)

```
root 안착 Y   1.08      = 바닥상면 0 + skinWidth 0.08 + height/2 1.0
눈            1.83      EyeOffset (0, 0.75, 0)
Body 중심     0.88      capsule h1.6 r0.5,  범위 0.08 ~ 1.68
Head 중심     1.83      sphere  r0.25,      범위 1.58 ~ 2.08
```

**머리 중심이 눈높이와 정확히 같다.** 머리로 가는 조준선이 완전한 수평선이 되므로, 1.83 미만의 엄폐물은 거리와 무관하게 머리를 가리지 못한다.

### 2.3 반차폐 사다리

V-LOS 는 몸통 중심 한 점만 판정한다. 따라서 오탐은 **"몸통 중심은 가려졌는데 사람 눈에는 보이는"** 높이대에서만 발생한다. 엄폐물 높이를 그 구간을 가로지르도록 역산해 배치했다.

| 높이 | 몸통 중심 (사수 10m 기준) | 머리 | 단일 판정 |
|---|---|---|---|
| 0.60 | 보임 | 보임 | 비차폐 (대조군) |
| 1.00 | 표적이 엄폐물 뒤 1.4m 내면 가림 | 보임 | 오탐 (경계) |
| 1.45 | 표적이 엄폐물 뒤 3.8m 내면 가림 | 보임 | **오탐 (주력)** |
| 1.90 | 가림 | 가림 | 정상 차폐 |
| 3.00 | 가림 | 가림 | 완전차폐 벽 |

이 사다리는 오탐을 유도할 뿐 아니라, 두 점 판정(머리·몸통)으로 수정했을 때 실제로 고쳐졌는지 검증하는 대조군도 제공한다.

## 3. 규칙별 임계값

### V-MOVE-01 — 이동 입력 검증

| 파라미터 | 값 | 근거 |
|---|---|---|
| `RefillPerSec` | 75/s | 정상 입력율 60/s + 25% 여유. 여유가 0이면 잔량이 랜덤워크가 되어 지터만으로 반드시 고갈된다 (5.3 참조) |
| `BucketCapacity` | 90 | 1.5초 분량. 실측 RTT 스파이크 1106ms 를 흡수해야 한다 |
| `SustainedDrainSec` | 1.0s | 이 시간 이상 연속 고갈일 때만 기록. 히컵은 짧고 치트는 지속된다 |
| `MaxTickJump` | 120 | 2초분. 패킷 손실로 입력이 통째로 유실될 수 있다 |
| `SpawnGraceSec` | 3.0s | 접속 직후 입력이 몰려 도착한다 (실측: client_tick 104 에서 11개) |

**탐지 신호**: 위치 변화량이 아니라 **입력 수신율**.

서버가 입력만 받아 직접 시뮬레이션하므로 서버가 만든 위치 델타는 정의상 상한을 넘을 수 없다. 실제 스피드핵은 클라이언트 시간을 조작해 `FixedUpdate` 를 더 자주 돌리므로, 관측 가능한 신호는 입력 개수뿐이다.

**조치**: 차단이 아니라 무시. 위반 입력은 `Simulate()` 를 호출하지 않는다. 클라이언트는 예측이 어긋나 다음 재조정에서 되돌아온다.

**탐지 지연**: 2배 스피드핵(120/s) 기준 용량 90 이 비는 데 2초 + 지속 판정 1초 = 약 3초. 3배면 약 1.9초.

### V-FIRE-01 — 발사 속도 검증

| 파라미터 | 값 | 근거 |
|---|---|---|
| 충전율 | 15/s | 정상 발사율 10/s × 여유 1.5 |
| `BucketCapacity` | 12 | 1.2초 분량 |
| `SustainedDrainSec` | 0.5s | 지터는 짧고 연사핵은 지속된다 |
| `SpawnGraceSec` | 2.0s | |

**탐지 신호**: 서버 실시간 기준 발사 빈도.

클라이언트 틱은 클라이언트가 만드는 값이라 신뢰할 수 없다. 게임플레이 게이트는 틱으로, 치트 검증은 서버 실시간으로 이중화했다.

연사핵의 공격 방식 — 입력 개수는 60/s 그대로 두고 틱 번호만 부풀린다. 그러면 틱 간격 게이트를 매번 통과하고 V-MOVE 도 개수만 보므로 걸리지 않는다. 실시간 발사율만 6배가 된다.

**탐지 지연**: 연사핵 60/s vs 충전 15/s, 용량 12 → 0.27초에 고갈, 지속 판정 0.5초를 더해 약 0.8초.

### V-LOS-01 — 시야 검증

| 파라미터 | 값 |
|---|---|
| 가시성 루프 주기 | 20Hz (60틱 / TickDivisor 3) |
| 추적 판정 콘 | 5° |
| `peakTrack` 임계 | 2.0초 |
| `ForgetSec` | 0.5초 |
| `OccludeMargin` | 0.05m |

두 갈래로 나뉜다.

#### (a) BlockedHit

되감은 세계에서 벽이 더 가까운데 히트가 성립하면 발화. **원리상 발화하지 않는다.**

그럼에도 넣은 이유: W7 Day 1 에 플레이어 루트가 `Default` 레이어에 있어 히트스캔이 되감긴 히트박스가 아니라 현재 위치 캡슐을 맞힌 적이 있다. 되감기가 조용히 무시되고 있었다.

0건으로 남는 것이 정상이고, **그 0 자체가 "레이어 설정이 맞다"는 근거**가 된다.

전 측정에서 0건.

#### (b) OccludedTracking

차폐된 적을 5° 콘 안에서 2초 이상 추적하면 발화. 월핵의 신호.

**현재 한계**: 몸통 중심 한 점만 판정한다. 몸통은 가려지고 머리는 보이는 상황에서 오탐이 가능하다. 7절 참조.

**조치**: 기록만.

### V-TIME-01 — 반응시간 검증

| 파라미터 | 값 | 근거 |
|---|---|---|
| `ThresholdMs` | 110ms | 인간 시각-운동 반응 하한 |
| `SpotQuantizationMs` | 50ms | 20Hz 루프 주기. 측정치가 실제보다 최대 이만큼 빠르다 |
| **실효 임계** | **60ms** | 110 − 50 |
| `EngagementWindowSec` | 3.0s | 재조우 판정 (5.1 참조) |
| `WindowSize` / `RepeatLimit` | 20 / 5 | 최근 20회 중 5회 이상이면 심각도 상향 |

**측정 대상**: SPOT(적이 화면에 뜬 순간)부터 첫 발사가 서버에 도착하기까지.

#### 보정 1 — RTT 정규화

```
raw      = fireArrival − spotTime = reaction + RTT/2
adjusted = raw − RTT/2
```

클라이언트 보고 RTT 는 쓰지 않는다. 부풀려서 관용 범위를 넓힐 수 있다.

#### 보정 2 — 20Hz 양자화

가시성 루프가 20Hz 라 실제 시야 확보보다 최대 50ms 늦게 SPOT 을 잡는다. SPOT 시각이 늦어지면 반응시간은 그만큼 짧게 측정된다.

판정에 50ms 를 더해, **가장 관대하게 해석해도 인간이 불가능한 속도일 때만** 잡는다.

#### 보정 3 — 연사·재조우 게이트

5.1 참조.

#### 왜 차단하지 않는가

코너를 미리 겨누고 있다가 적이 나타나면 사람도 0ms 에 가까운 반응이 나온다. 정당한 플레이다.

단발은 심각도 1로 기록만, 최근 20회 중 5회 이상이면 심각도 3. **차단은 하지 않는다.** W13 Trust Score 의 입력으로 쓴다.

## 5. 발견한 오탐 원인

### 5.1 V-TIME — 연사 도중 발사를 반응으로 측정

match 44 에서 13건. 치트 미사용.

`combat_events` 를 SPOT 과 조인해 반응시간과 `shot_index` 를 함께 보았다.

| raw_ms | shot_index |
|---|---|
| 4.0 | 15 |
| 6.0 | 10 |
| 10.0 | 19 |
| 16.0 | 13 |

**연사 도중이었다.** `shot_index` 19 는 발사 버튼을 계속 누른 채 20번째 총알이 나간 것이다.

교전 중 상대가 잠깐 시야에서 벗어났다 돌아오면 `ForgetSec`(0.5초) 경과로 새 `spotId` 가 발급된다. 그 순간 사수는 이미 발사 버튼을 누르고 있으므로, 다음 발사 게이트가 열리는 즉시 총알이 나가 4ms 가 측정된다.

기존 규칙("같은 spotId 를 두 번 재지 않는다")으로는 걸러지지 않는다. spotId 가 새 값이기 때문이다.

13건 중 3건은 `shot_index = 0` 이었다. 연사를 잠깐 멈췄다 재개한 경우로, 총구는 계속 상대를 향하고 있었다.

**수정**: 게이트 두 개 추가.

1. `shotIndex > 0` → 트리거를 이미 당기고 있었으므로 반응이 아니다
2. SPOT 시각 기준 3초 내에 같은 표적에게 발사한 적 있음 → 재조우이지 첫 조우가 아니다

게이트 2 의 비교 기준을 `now` 가 아니라 **`spotTime`** 으로 잡는 것이 중요하다. `now` 로 비교하면 연사 중 마지막 발사 시각이 계속 갱신되어, 한 번 교전한 상대는 영원히 측정되지 않는다. `spotTime` 기준이면 **시야가 끊겨 있던 시간**을 재게 되어 의도한 판정이 된다.

두 게이트 모두 측정 횟수를 줄이기만 한다. 트리거봇의 신호는 "처음 조준선에 들어온 순간 발사"이므로 첫 조우에서 여전히 탐지된다 (6절에서 확인).

### 5.2 V-FIRE — 거부가 게이트를 멈춰 연쇄 증폭

match 51 에서 169건. 치트 미사용.

| first_tick | last_tick | occurrences |
|---|---|---|
| 21896 | 21955 | 60 |
| 21956 | 22015 | 60 |
| 22016 | 22064 | 49 |

**틱 폭 59에 60건 = 매 틱마다 1건.** 60은 치트 배율이 아니라 서버 틱레이트였다.

연사핵이었다면 틱을 6씩 부풀리므로 60건에 360틱 폭이 나와야 한다 (6절 탐지 확인 로그와 비교).

#### 원인 (1) 충전율에 여유가 없었다

```
refill = TickRate / FireIntervalTicks = 60/6 = 10/s
게임플레이 게이트도 정확히 10/s 허용    →  여유 0
```

여유가 0이면 토큰 잔량이 **랜덤워크**가 된다. 지터로 오르내리다 언젠가 반드시 0에 닿는다. 시간 문제일 뿐이다.

#### 원인 (2) 거부가 게이트를 멈췄다 ★ 169건의 직접 원인

```csharp
if (input.tick - _lastFireTick < FireIntervalTicks) return;   // 게임플레이 게이트

if (!_fireValidator.TryFire(now, out var reason)) {
    ViolationLogger.Report(...);
    return;                      // ← _lastFireTick 갱신 안 됨
}
_lastFireTick = input.tick;      // 성공했을 때만
```

버킷이 비면 `_lastFireTick` 이 그 시점에 멈춘다. 이후 `input.tick − _lastFireTick` 이 계속 커지므로 **게임플레이 게이트가 모든 틱을 통과시킨다.** 소비 60/s, 충전 10/s — 발사 버튼을 뗄 때까지 회복 불가.

실측에서 3초간 지속되다 멈춘 것이 이 때문이다(버튼을 뗌).

**수정**

1. 충전율을 정상 발사율의 1.5배(15/s), 용량 12
2. 지속 고갈 요건 0.5초 — 순간 고갈은 차단만 하고 기록하지 않는다
3. `WeaponSystem` 에서 거부 시에도 `_lastFireTick` 을 전진시켜 연쇄를 끊는다

연사핵은 틱을 부풀리므로 게이트를 계속 통과한다. 탐지는 유지된다.

## 반동 인덱스 축 불일치 (W8 사전 측정)

`RecoilResetTicks = 21` (약 0.35초) 기준, match 57 실측.

| 기준 | 불일치 | 전체 | 비율 |
|---|---|---|---|
| 발사 | 2 | 1304 | 0.28% |
| 버스트 | 2 | 144 | 1.4% |

플레이어별로는 player 1 이 2/84 (2.4%), player 19 가 0/60 (0%).

**배경**
연사 중단 판정 기준이 클라와 서버에서 다르다.

| | 판정식 | 축 |
|---|---|---|
| 클라 `_clientShotIndex` | `tick - _clientLastFireTick > RecoilResetTicks` | 클라 틱 |
| 서버 `_shotIndex` | `now - _lastFireRealtime > RecoilResetTicks / 60` | 서버 실시간 |

서버가 실시간을 쓰는 것은 의도된 설계다. 틱으로 판정하면 틱을 크게
점프시켜 매 발을 `shot_index = 0` 으로 만들 수 있고,
`expected_recoil_pitch` 가 항상 0 이 되어 노리코일 탐지가
비교할 기준선을 잃는다. 대가로 두 축이 갈라질 수 있다.

**결론**
0.28% 는 8발 연사 시 누적 세로 반동 약 6도 대비 무시 가능한 수준이다.
`expected_recoil_pitch` 를 노리코일 탐지 기준선으로 사용 가능.

**설계 제약**
버스트 기준으로는 1.4~2.4% 다. 한 번 어긋나면 그 연사 전체가
오염되므로 이쪽이 실질적 오차 바닥이다.
따라서 노리코일 판정은 단일 버스트가 아니라
최근 N 개 버스트 중 M 개 이상 형태의 창 기반이어야 한다.
V-TIME-01 의 WindowSize / RepeatLimit 와 같은 구조.

**참고 수치 (match 57)**
- 총 1304 발 / 144 버스트 = 평균 9.1 발
- `RecoilRampShots = 8` 이므로 대부분의 버스트가 램프를 끝까지 밟는다

**측정 방법 주의**
위 수치는 `client_tick` 간격으로 클라 판정을 역산한 값이다.
`client_tick` 이 단조 증가한다는 가정이 필요하므로
rapidfire 처럼 틱을 부풀리는 치트 세션에서는 이 방법이 깨진다.
치트 측정에는 새로 추가한 `fire_gap_ticks` / `fire_gap_ms` 를 쓴다.
서버가 그 순간 직접 잰 값이라 가정이 필요 없다.


## V-RECOIL-01 노리코일 탐지 (W8 Day 2)

통계량  버스트 내 연속 20발의 comp 표본 표준편차
        comp = (pitch[n] - pitch[n-1]) + GetRecoil(n).y
임계    comp_sd < 0.3 → 위반 (잠정)

### 실측

| 매치 | 라벨 | 발수 | comp_mean | comp_sd |
|---|---|---|---|---|
| 63 | clean | 579 | 1.089 | 0.850 |
| 64 | clean | 785 | 1.084 | 0.870 |
| 65 | cheat | 600 | 1.097 | **0.096** |

match 62(mixed)의 노리코일 구간은 sd 0.250~0.290.
match 57(clean)은 player 1 이 1.124, player 19 가 2.153.

### 핵심

comp_mean 이 세 매치 모두 1.08~1.10 으로 동일하다.
잘하는 플레이어는 반동을 거의 전부 상쇄하므로 평균으로는
노리코일과 구분되지 않는다. 구분되는 것은 편차다.
사람은 손으로 따라가느라 흔들리고 핵은 기계적으로 정확하다.

comp_min 도 보조 지표가 될 수 있다.
정상은 음수가 나오지만(-0.30 / -0.20) 노리코일은 최소 0.30 으로
음수가 한 번도 없다. 반동을 상쇄할 필요가 없기 때문이다.
현재는 comp_sd 만으로 충분히 갈리므로 쓰지 않는다.

### 임계 근거

정상 하한 0.850 / 노리코일 상한 0.290.
임계 0.3 이면 양쪽으로 2.8배 및 3배 여유.
0.5 는 정상 하한과 1.7배 차이뿐이라 위험하다.

### 한계

63~65 는 모두 동일 플레이어 1명이다. 개인차가 반영되지 않았다.
정상 하한 0.850 은 잠정값이며 다른 플레이어로 검증해야 한다.
match 57 기준 개인차는 최대 2.5배(1.124 vs 2.153).

### 재현 쿼리

```sql
WITH s AS (
  SELECT
    match_id, player_id, client_tick, shot_index, pitch,
    LAG(client_tick) OVER (PARTITION BY match_id, player_id ORDER BY client_tick, id) AS prev_tick,
    LAG(pitch)       OVER (PARTITION BY match_id, player_id ORDER BY client_tick, id) AS prev_pitch
  FROM combat_events
  WHERE match_id IN (?, ?)
    AND event_type IN ('FIRE','HIT','KILL')
)
SELECT match_id, player_id, COUNT(*) AS n,
       ROUND(AVG(comp), 3) AS comp_mean,
       ROUND(STDDEV_SAMP(comp), 3) AS comp_sd
FROM (
  SELECT match_id, player_id,
         (pitch - prev_pitch) + (0.4 + 0.7 * LEAST(shot_index / 8.0, 1.0)) AS comp
  FROM s
  WHERE prev_tick IS NOT NULL
    AND client_tick - prev_tick <= 21
    AND shot_index > 0
) t
GROUP BY match_id, player_id;
```

측정 절차: 세션마다 게임 서버를 재시작해야 match_uid 가 새로 발급된다.
클라이언트만 재접속하면 같은 매치에 계속 쌓인다(match 62 가 그 사례).


서버 구현 검증 (match 67, 노리코일 ON, 조준 고정)
  samples=244 evaluated=187 violations=2 bursts=2 minSd=0.000
  창 20발이 차는 시점(shotIndex=20)에 즉시 판정.
  히스테리시스 정상 — 버스트당 1건.

  ※ 조준을 완전히 고정해 sd=0 이 나왔다. 탐지 작동 증명으로는
    유효하나 임계 근거로는 쓰지 않는다. 임계는 조준을 유지한 채
    측정한 match 62(0.250~0.290) / match 65(0.096) 기준.

**원인**

매치 단위 집계(0.850)와 창 단위 최저값(0.228)은 다른 값이다.
전자로 임계를 정하고 후자로 판정한 것이 오류였다.

창 20발은 10발/초 기준 2초다. 사람이 손을 고르게 유지할 수 있는
시간이며, 400발 이상의 세션에서는 그런 구간이 우연히 발생한다.

|---|---|
| 63 | 0.850 |

**왜 창을 키우지 않는가**

40발 창이면 2초가 4초가 되어 우연이 줄어든다. 그러나 탄창(30발)이
구현되면 40발 연속 발사가 불가능해져 창이 영원히 차지 않는다.
현재 탄약이 무한이라 가능한 것일 뿐, 확장성이 없는 해법이다.

**변경 — 2단계 판정**

V-TIME-01 의 WindowSize / RepeatLimit 구조를 차용했다.
한 번 낮은 것은 우연이고, 계속 낮은 것은 우연이 아니다.

1단계 창 20발의 표본 편차 < 0.30 → "의심" 1회로 센다. 보고 안 함.
2단계 최근 30회 판정 중 20회 이상이 의심 → 그때 보고.
의심이 8회 이하로 떨어지면 다음 에피소드를 다시 보고할 수 있다.


의심 이력은 버스트 경계를 넘어 이어진다. 노리코일은 연사를 끊어도
계속 켜져 있기 때문이다. 창(_window)만 버스트마다 비운다.

**측정 불가였던 값**

기존 구현은 히스테리시스가 보고를 막아 "의심 판정이 실제로 몇 번
있었는지"를 기록하지 않았다. match 68 의 위반 1건이 의심 1회인지
20회인지 알 수 없다. SuspiciousEvaluations 카운터를 추가했으며,
20/30 은 그 실측 전까지 잠정값이다.

**다음 측정에서 확인할 것**

| 세션 | 기대 |
|---|---|
| 정상 | suspicious / evaluated < 10% |
| 노리코일 | suspicious / evaluated > 90% |

정상 비율이 30% 를 넘으면 SuspicionLimit 을 올린다.
노리코일 비율이 90% 미만이면 SdThreshold 를 조정한다.
